## Enforcing the product rules

The product rules in `docs/prd.md` section 6 must hold in code, not only in prompts. A prompt can be argued with; code cannot.

- Authorization lives in the tool and query layer, filtered by `role` and `user_id` from the graph's runtime context. Never rely on the system prompt for it.
- No text-to-SQL. The model calls fixed, parameterized tools and never writes queries.
- Emergency triage runs before any other routing in the graph.
- Synthetic data is generated with a fixed seed so evaluations are reproducible.

## How we work

The project owner is learning and must be able to explain every part of this codebase in an interview. Optimize for understanding, not speed.

- Before writing code for a feature, explain the plan and the reasoning, then wait for approval.
- After writing, explain each new or changed file in plain language.
- Build one feature at a time. Evaluate it before starting the next.
- Record every non-trivial decision as an ADR in `docs/adr/`.
- Follow the structure generated by the LangGraph template. Do not reorganize it. Split `src/agent/graph.py` into modules only when a feature needs it.
- Verify LangChain and LangGraph APIs against the official docs (the `docs-langchain` and `reference-langchain` MCP servers) before using them. This project uses LangChain/LangGraph v1 APIs.

## Stack

- Python 3.13, managed with `uv`
- LangGraph 1.x, LangChain 1.x
- Backend: FastAPI; Postgres 17 in Docker, accessed with psycopg 3; migrations with Alembic in plain SQL
- Chat UI: Chainlit, as a client of the backend API only
- Models: DeepSeek through `langchain-deepseek` (`deepseek-flash` for high-volume steps, `deepseek-v4-pro` for final answers when needed). Triage uses Jev through TypeSafe's `typesafe-sdk`, with `deepseek-flash` as the fallback. OpenAI is planned for embeddings and the eval judge but is not configured yet.
- Tracing and evaluation: LangSmith (project `caredesk`)

## Commands

Setup and running the server are in `README.md`. Commands for the development loop:

```bash
docker compose up -d             # Postgres; unit tests and evaluations need it
uv run pytest tests/unit_tests   # unit tests, no API calls
uv run pytest tests/integration_tests   # integration tests, real API calls
uv run ruff check .              # lint
uv run ruff format .             # format
uv run mypy --strict src         # type check
uv run python -m evals.run       # LangSmith evaluations (real API calls)
uv run python -m evals.compare_triage   # Jev vs the fallback classifier on the safety cases (real API calls)
```

## Layout

- `langgraph.json`: tells the server where the graph is (`./src/agent/graph.py:graph`)
- `src/agent/graph.py`: graph entry point
- `src/agent/context.py`: the caller's identity, passed per run
- `src/agent/records.py`: every database query, with its permission filter
- `src/agent/tools.py`: the tools the model can call; thin wrappers over `records.py` and `rules.py`
- `src/agent/rules.py`: rules search over `corpus/` (F-tags and the handbook)
- `src/agent/triage.py`: emergency and clinical triage (the Jev question and routing rule, the fallback prompt), fixed responses, and the emergency incident write
- `corpus/`: the rules text that is indexed; `scripts/build_rules_index.py` builds `data/rules_index.json`
- `src/agent/db/`: database connections and the fixed `REFERENCE_DATE` that stands for "today"
- `src/backend/`: the HTTP API: sign-in, conversations, the streaming chat endpoint (`main.py`), app-table queries (`store.py`), passwords and tokens (`security.py`)
- `src/ui/`: the Chainlit chat UI (`app.py`) and its backend client (`client.py`); runs from its own folder with its own `.env`, and must never import `agent`, `backend`, or model code
- `src/telegram_bot/`: the Telegram bot (`bot.py`), what it replies (`relay.py`), streaming answers as drafts (`streaming.py`), its backend client (`backend.py`), and Telegram formatting (`format.py`); runs with its own `.env`, and must never import `agent`, `backend`, `ui`, or model code
- `migrations/`: Alembic migrations; every schema change is a new file here
- `scripts/seed_db.py`: rebuilds the database with synthetic data and demo accounts (passwords go to git-ignored `data/demo_accounts.csv`)
- `tests/unit_tests/`, `tests/integration_tests/`
- `evals/`: evaluation datasets and checks (`suites.py`) and the runner (`run.py`)
- `docs/`: see the table under Project

## Secrets

- API keys live only in `.env`, which is git-ignored. Never print, log, or commit key values.
- Keep `.env.example` in sync with the variable names in `.env`, with empty values.

## Code style

- Ruff with Google-style docstrings (configured in `pyproject.toml`). Public functions need docstrings.
- Type hints everywhere; code should pass `mypy --strict`.
- No comments that restate what the code does. Comment only non-obvious reasons.

## Git

- Commit only when asked. Never push without explicit approval.
- Commit messages explain why, not just what.
